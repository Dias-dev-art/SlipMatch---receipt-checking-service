    Our solution is Waitly: one Telegram bot for every shop. Each shop gets its own link, printed as a QR code. The customer scans it and an AI agent takes the order — it answers menu questions, understands Manglish, and asks for anything missing. Then the bot sends the shop's DuitNow QR with the exact amount and a reference. The owner checks the bank and taps Approve. Our core rule: AI talks, code decides. The AI can only act through tool calls that the backend validates, and it can never say a payment was received. [Name 2], over to you.

    Thanks. I built the backend with FastAPI, SQLModel and PostgreSQL. For every message, Telegram calls our webhook, and we build a prompt with the shop, its menu, the current cart and the missing fields. The model can't write into the order directly — it has exactly eight tools, like add item, set address and request payment. Every tool call is validated against the database: does the item exist, is it available. Prices come from the menu and totals are calculated in Python, never by the model. A reply guard blocks any message that claims an action the AI didn't actually take. Add timers, a reliable outbox and multi-tenant data, and the system stays correct. [Name 4], over to you.

    Thanks. I handled Replit and model tuning. Our app runs on a Replit Reserved VM, where one process serves the API, the Telegram webhook and the dashboard, with Replit PostgreSQL and all keys in Replit Secrets. For the AI, we started from Qwen 2.5 7B Instruct. The base model made real mistakes: on "itu je" it asked "ready to pay?" instead of calling request payment, and on "dah bayar" it sometimes said "payment confirmed" — which must never happen. So we generated synthetic dialogues using the exact production prompt and tools, and fine-tuned with LoRA using Unsloth and TRL. A model is ready only when it passes all eight of our real-conversation tests. [Name 5] will show how we serve it.

    Thanks. I deployed the model on RunPod. We serve the fine-tuned Qwen with vLLM on a GPU endpoint that speaks the OpenAI API, with tool calling. So the Replit backend doesn't care which model is behind it — switching from base to fine-tuned is just three environment variables, no code changes. Replies take about one and a half to seven seconds per turn, which feels natural in chat. Cold workers sometimes pushed that past forty seconds, so we added a sixty-second timeout with two retries and keep a warm worker for the demo. Back to [Name 1].
